Part 1

Setup: what differs between runs

All three runs use the same topology, traffic, seed and duration. The only thing that changes is the utility A passed to each flow's congestion controller. That utility scales how strongly the flow reacts to ECN marks (p' = p / (A + (1 − A)·p)).

Interpretation

✔ Allocation responds

Utility weights reliably shift throughput toward higher-utility flows, and the dynamic schedule visibly re-shapes congestion windows within seconds of each change.

✖ No overall gain yet

Weighted satisfaction is flat: 0.724 (E1), 0.720 (E2), 0.722 (E3). Winning flows gain about as much as losing flows give up.

⚠ Latency cost

Gentler back-off by high-utility flows builds a larger standing queue: L4S sojourn p99 rises from 5 to 19 ms and p95 delay by 12–15 ms.

Limitations

  • DCTCP proxy: no TCP Prague or Accurate ECN in this checkout. These are not TCP Prague results.
  • Single seed: one run per experiment, so there is no variance or significance estimate.
  • One operating point: 10 Mbps / 10 ms and roughly 150% offered load only.
  • Histogram percentiles: FlowMonitor delay percentiles are bin-edge estimates.

Next steps: multiple seeds, bottleneck and load sweeps, and a true L4S sender. See project progress.
