Industrial AR traffic over an L4S dual-queue bottleneck

An ns-3 simulation study. Four industrial augmented-reality applications share a 10 Mbps DualPI2 (L4S + Classic) bottleneck. We test whether giving each application a utility weight in its congestion control lets the network favour the traffic that matters most, including when those priorities change during a task.

Project objectives

The project builds a reproducible simulation testbed and uses it to answer one question: does application-aware weighting of the L4S congestion response improve how a shared bottleneck serves industrial AR workloads?

1

Model the workload

Represent an industrial AR session as four concurrent flows: remote video, 3D work instructions, sensor telemetry and maintenance logs, each with a realistic offered load.

2

Build the bottleneck

Place the flows behind an L4S/Classic DualPI2 coupled queue in ns-3 and instrument it for queue occupancy, sojourn time, ECN marks and drops.

3

Add utility weights

Extend the ECN-based congestion response so each flow's reaction to marking is scaled by an application utility weight between 0 and 1.

4

Compare policies

Run three experiments (equal weights, fixed weights, and weights that change with the operator's activity) under identical conditions.

5

Measure what matters

Report per-application throughput, satisfaction, p95/p99 delay, jitter, ECN marking, queue occupancy and a weighted utility score.

6

Stay reproducible

Ship the scenario, analysis and plotting scripts so every number and figure can be regenerated from one set of commands.

Problem statement

Industrial AR headsets stream video to a remote expert, pull 3D overlays, report machine sensors and upload logs, all over the same wireless or access link. These flows matter differently, and how much each one matters changes with the task: during remote assistance the video is critical, during component inspection the 3D instructions are, and during an overheating alarm the sensor feed is.

L4S (Low Latency, Low Loss, Scalable throughput) with a DualPI2 coupled queue keeps queueing delay very low for scalable, ECN-capable flows. But L4S congestion controllers treat every flow the same: each backs off by the same rule when packets are marked. The network has no way to know that one flow is more important than another right now.

Research question

If each flow's congestion response is weighted by an application utility, and those utilities follow the operator's current activity, does the bottleneck deliver better weighted application satisfaction than equal-weight L4S, without giving up its latency benefits?

Why it is hard

  • Bandwidth is scarce: offered load is about 15 Mbps on a 10 Mbps link.
  • Priorities shift mid-session, so a fixed weighting is not enough.
  • Changing the response must not raise queueing delay or loss.

Methodology

Everything runs in ns-3 (Waf build). A single scenario program, industrial-ar-dualq, takes an --experiment flag and writes all metrics to CSV and FlowMonitor XML, which Python scripts then merge and plot.

Utility-weighted congestion response

The ns-3 checkout has no TCP Prague or Accurate ECN, so TcpDctcp is used as the ECN-capable L4S proxy. On each window reduction, the measured marking fraction p is mapped through the application utility A before DCTCP cuts its window:

p' = p / (A + (1 − A)·p)          // A = application utility (0, 1]
cwnd ← max( (1 − p'/2) · cwnd , 2·MSS )

With A = 1 this is plain DCTCP. A flow with a higher utility reacts more gently to the same marking and keeps a larger share; a low-utility flow backs off harder. Utilities are set per socket at run time through TcpSocketBase::SetCongestionControlUtility.

Experiments

E1 · Equal utility

Every flow uses utility 1.0 for the whole run. This is the unmodified DCTCP baseline.

E2 · Fixed utility

Video 0.9, instructions 0.6, sensors 0.5, logs 0.2 for all 100 s (remote-assistance profile).

E3 · Dynamic utility

Utilities follow the activity schedule below and change at 30, 60 and 80 s.

Workflow

Build

./waf configure --enable-examples then ./waf build

Simulate

Run E1, E2, E3 for 100 s each with the same seed

Trace

FlowMonitor, cwnd, queue (10 ms), sojourn and per-app CSVs

Analyze

industrial-ar-analyze.py merges runs into comparison.csv

Plot

Per-experiment and cross-experiment figures

Metrics

  • Satisfaction per app: min(throughput / offered load, 1).
  • Weighted utility satisfaction: satisfaction weighted by each app's time-averaged E3 utility, normalized by the sum of those utilities. The same weights score all three experiments so they are comparable.
  • Delay: p95/p99 from FlowMonitor histograms; jitter and loss per flow.
  • Network: ECN marking ratio, drops, aggregate queue occupancy p95, Classic and L4S sojourn p99.
